## DB-ADR-001 — Surrogate BIGINT primary keys with a public UUID

**Status:** Accepted

**Context.** Every table needs an identifier strategy, and it is effectively
irreversible once foreign keys and client-held references exist. Three candidates
were considered: `BIGINT AUTO_INCREMENT`, UUID (v4 or v7) as the primary key, and
natural keys such as email or recipe slug.

**Decision.** Entity tables use `id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT` as
the primary key. Tables whose rows are addressed from outside the backend
additionally carry `public_id BINARY(16)` — a UUID in raw bytes with a unique
index — and the REST API exposes only `public_id`. Pure association tables use a
composite primary key of their two foreign keys and no surrogate. Reference
vocabularies additionally carry a unique `code VARCHAR` used by migrations,
seeds and Java enums.

**Rationale.**

- InnoDB clusters rows on the primary key, so a monotonically increasing value
  appends at the right edge of the B-tree. A random UUID primary key scatters
  inserts, causing page splits, and every secondary index carries the 16-byte key
  instead of 8. With 88 foreign keys, that cost is paid everywhere.
- Sequential ids must not be exposed: `GET /api/v1/users/1042` invites
  enumeration and leaks how many users exist. `public_id` gives the API an opaque
  handle while joins stay on the narrow integer.
- `BINARY(16)` rather than `CHAR(36)`: 16 bytes against 36, and MySQL 8 has
  `UUID_TO_BIN`/`BIN_TO_UUID` for conversion at the boundary.
- Natural keys were rejected as primary keys because they change. An email
  correction or a recipe retitle would have to propagate through every child row.
  Both are kept as unique constraints instead.

**Consequences.** Java entities use `@GeneratedValue(strategy = IDENTITY)`, which
prevents JDBC batch inserts of new entities — acceptable, since bulk insert is
not a product path. `public_id` must be generated by Java on insert (UUIDv7 is
preferred for index locality) and mapped to a `byte[]`. Code and API contracts
must never surface `id`. Two indexes exist per public entity instead of one.

**Rejected alternatives.** UUID as primary key: portable and generatable
client-side, but the write amplification and index bloat are unjustified here. A
`hashids`-style reversible encoding of `id`: obscures rather than removes
enumeration. A single global id sequence: no benefit without sharding.

## DB-ADR-002 — Relational columns, not JSON

**Status:** Accepted

**Context.** MySQL 8 has a capable `JSON` type. Several parts of this domain look
superficially like documents: a food's nutrient set, a user's dietary
preferences, a recipe's step list, an AI result's component scores. Modelling
those as JSON would cut the table count substantially.

**Decision.** No `JSON` column exists in this schema. Every structure above is
relational.

**Rationale.** Each of those structures fails at least one JSON requirement:

- **Referential integrity.** A nutrient inside a JSON blob cannot have a foreign
  key to `nutrients`. A typo'd nutrient code would be stored happily and surface
  as a missing value months later.
- **Querying.** "Foods with more than 20 g protein per 100 g" over
  `ix_food_nutrients_nutrient_amount` is a range scan. Over JSON it is a full
  scan with per-row extraction, or a functional index per nutrient — at which
  point the relational table is simpler.
- **Partial update.** Marking one meal entry as eaten is a single-row `UPDATE`.
  In a JSON plan document it is a read-modify-write of the whole plan, which
  reintroduces the lost-update problem that `version` columns exist to prevent.
- **Aggregation.** "Average protein across accepted plans" is a `JOIN` and an
  `AVG`. Over JSON it needs `JSON_TABLE` and cannot use an index.

**Consequences.** More tables (53) and more joins. The team writes more JPA
mappings. In exchange, the database validates the data, the query planner can
optimise, and a malformed structure is rejected at write time rather than
discovered at read time.

**When JSON would be acceptable.** A payload that is written once, read back
whole, and never used as a query predicate — a raw AI response body kept for
debugging, or a serialised client preference bundle with no server-side meaning.
No such need exists in P2. A future ADR may add one; it must state which queries
will *not* be run against it.

**Rejected alternatives.** JSON for nutrition, preferences, steps and scores, for
the reasons above. A hybrid "relational plus JSON overflow column": in practice
the overflow column accumulates fields that later need querying, and migrating
them out is worse than not starting.

## DB-ADR-003 — Lookup tables for referenced vocabularies, CHECK constraints for branch values

**Status:** Accepted

**Context.** The design has roughly 30 controlled vocabularies. Making every one
a table would add 18 more tables of two to six rows each, most joined on every
read. Making every one a string would lose referential integrity where other
tables genuinely reference the value.

**Decision.** One test decides: **does anything need to reference, extend, or
attach attributes to this value?**

*Lookup table* (12 in P2, plus `ingredient_groups`): `roles`,
`measurement_units`, `nutrients`, `activity_levels`, `nutrition_goals`,
`dietary_preferences`, `allergens`, `meal_slot_types`, `food_categories`,
`recipe_tags`, `ai_score_components`, `notification_types`. Each is the target of
at least one foreign key, or carries its own attributes (a unit's conversion
factor, an activity level's energy factor, a score component's declared scale),
or will be extended by non-developers.

*`VARCHAR` + `CHECK` + Java enum*: `users.account_status`, `recipes.status`,
`recipes.difficulty`, `meal_plans.status`, `pantry_items.status`,
`pantry_items.expiry_kind`, `pantry_items.expiry_confidence`,
`pantry_items.storage_location`, `meal_plan_entries.provenance`,
`meal_plan_entries.consumption_status`, `pantry_item_events.event_type`,
`notifications.status`, `recommendation_requests.status` and `request_kind`,
`recommendation_results.user_decision`,
`ingredient_substitutions.confidence`/`sensory_impact`/`substitution_context`,
`ingredient_foods.preparation_state`, `ingredient_allergens.presence`,
`user_allergens.reaction_kind`, `user_disliked_ingredients.strength`,
`user_account_events.event_type`, `user_auth_sessions.client_kind` and
`revocation_reason`, `user_security_tokens.token_kind`,
`user_nutrition_targets.origin`, `user_body_measurements.source`,
`foods.source`/`nutrition_basis`, `food_nutrients.data_quality`,
`search_queries.search_scope`, `user_profiles.sex`.

Every one of those constrains a single column and is branched on in Java. Adding
a value requires a code change regardless, so a table row would not avoid a
deployment — it would only add a join.

MySQL's native `ENUM` type is used nowhere.

**Rationale.** The lookup tables are the ones whose values are *data*: a
nutritionist can add an allergen without a developer, and `measurement_units`
needs `factor_to_base_unit` to exist somewhere. The `CHECK` values are the ones
that are *code*: `PENDING` versus `SENT` means nothing without the delivery
worker that interprets it. `ENUM` was rejected because it stores ordinals — value
reordering silently rewrites meaning — adding a value needs `ALTER TABLE`, and
JPA maps it as a string anyway, so the type buys nothing over a `CHECK`.

**Consequences.** Two patterns exist and the team must apply the test rather than
copy the nearest example. Adding a `CHECK` value requires a migration to widen
the constraint, which is a deliberate, reviewable step. Java enum values and
`CHECK` lists must be kept in step; a mismatch surfaces as a constraint violation
in integration tests, which is the failure mode we want.

**Rejected alternatives.** All-tables: 18 extra joins for values that are already
compiled into Java. All-strings: loses the foreign keys on
`user_allergens.allergen_id` and friends, which is where integrity actually
matters. Native `ENUM`: ordinal fragility.

## DB-ADR-004 — Flyway-compatible, forward-only migrations

**Status:** Accepted

**Context.** Four people will change the schema concurrently for the rest of the
project. Hibernate's `hbm2ddl.auto` can generate schema from entities; Flyway and
Liquibase manage explicit migrations. P1 (ADR-004) already committed to
"controlled migrations" without naming a tool.

**Decision.** Version-controlled SQL files under `database/schema/`, named to
Flyway's versioned convention (`V001__initial_schema.sql`), applied in order,
**immutable once applied**, forward-only. Reference data lives in
`database/seed/` as a *repeatable* migration (`R001__reference_data.sql`).
`spring.jpa.hibernate.ddl-auto` will be `validate` in every environment, never
`update` or `create`.

**Rationale.**

- `hbm2ddl.auto=update` never drops or renames, produces no reviewable artifact,
  gives no control over index or constraint naming, and differs subtly by
  Hibernate version. It cannot be the schema authority.
- Plain SQL is reviewable in a pull request by anyone who reads SQL, requires no
  XML or YAML abstraction, and is exactly what runs. Liquibase's changelog
  abstraction buys database portability this project does not need — MySQL is
  fixed by ADR-004.
- Immutability is what makes checksums meaningful. If `V001` may be edited after
  it has been applied, no two environments are known to match.
- Forward-only, with no `undo` scripts: an automated rollback of a schema change
  that has already accepted writes discards user data. Recovery is a new forward
  migration plus a restore if needed.
- `ddl-auto=validate` turns entity/schema drift into a startup failure rather
  than a silent runtime mismatch.

**Contract every migration file obeys** (mechanically checkable):

1. No `CREATE DATABASE` or `USE` — the target schema comes from the connection.
2. No `CREATE USER`, `GRANT`, or any credential. Provisioning is deployment's
   job, and a migration is a public artifact in git.
3. No `DROP`, `TRUNCATE`, or unqualified `DELETE` in `V001`. It must be safe to
   run against a populated database: it will fail on an existing table rather
   than destroy one.
4. Tables in foreign-key dependency order; `FOREIGN_KEY_CHECKS` is never
   disabled. A clean load therefore proves the dependency graph.
5. Explicitly named constraints, per the naming conventions.
6. `R00x` files are idempotent (`INSERT ... ON DUPLICATE KEY UPDATE` on a natural
   key) and never delete.

**Consequences.** Every schema change is two steps — write the entity, write the
migration — and the team must not skip the second. Flyway is not yet a
dependency; it is added when Spring Boot is scaffolded in a later phase, and
these files are adopted unchanged. A generated `flyway_schema_history` table will
appear then; it is not part of P2. Local development starts from `V001` plus
`R001`, so every developer has an identical schema.

**Rejected alternatives.** `hbm2ddl.auto=update` as the authority: not
reviewable, not deterministic. Liquibase: portability abstraction with no
beneficiary here. A single evolving `schema.sql`: loses version identity, and
diffs stop telling you what changed in production. Undo scripts: data loss
disguised as safety.

## DB-ADR-005 — Derived values are computed, not stored, except as dated snapshots

**Status:** Accepted

**Context.** The domain is full of values derivable from others: BMI from height
and weight, age from birth date, BMR/TDEE from profile and activity, recipe
nutrition from ingredient nutrition, plan-day totals from entries, current weight
from measurement history. Storing a derived value risks staleness; recomputing it
risks cost.

**Decision.** Derived values are computed on read by default. Three exceptions,
each with a stated reason:

1. **Generated columns** where the database maintains the value and something must
   index or constrain it: `users.email_normalized`, `recipes.total_minutes`,
   `meal_plans.day_count`. All `STORED`, so they are indexable.
2. **Recipe nutrition snapshots** — `recipe_nutrition_snapshots` +
   `recipe_nutrition_values` — which record a computation with `computed_at`,
   `ingredient_revision`, `completeness_ratio` and `is_current`.
3. **`pantry_items.quantity_remaining`**, a running total maintained alongside the
   `pantry_item_events` trail that could reproduce it.

Explicitly **not** stored: BMI, age, BMR, TDEE, current weight, plan-day nutrition
totals, pantry item counts.

**Rationale.**

- BMI is one arithmetic expression over two columns in the same aggregate. A
  stored copy is wrong from the moment a new weight is recorded, and there is no
  query that needs to filter on it. Age likewise: `birth_date` is the fact, and a
  stored age is wrong within a year.
- Current weight is *not* a profile column, because weight history is a feature;
  the newest `user_body_measurements` row is a single index seek.
- Recipe nutrition is the real exception. Computing 20 nutrients across a dozen
  ingredients — each needing an ingredient→food mapping, a serving conversion and
  a yield factor — for every row of a search result page is not viable. More
  importantly the derivation is **not stable**: correcting a food's protein value
  would retroactively change the nutrition of every meal already eaten. A dated
  snapshot keeps history honest, which is exactly what the report needs.
- `completeness_ratio` is what stops a snapshot from lying: a total computed from
  nine of twelve ingredients is not comparable to a complete one, and the ratio
  lets the client label it instead of presenting a confident wrong number.
- `quantity_remaining` avoids aggregating an item's whole event history on every
  pantry list render. The single writer keeps it consistent within a transaction,
  and `ck_pantry_items_quantity_remaining` bounds it.

**Consequences.** Java owns the formulas, in one place, unit-tested — which is
better for the coursework than SQL expressions scattered across queries.
Snapshots must be invalidated when a recipe's ingredients change or a referenced
food's `revision` increments; that is a recomputation job, and `is_current` plus a
functional unique index guarantee at most one current snapshot per recipe.
Historical snapshots are kept, not overwritten.

**Rejected alternatives.** Storing BMI and age: staleness with no query benefit.
Computing recipe nutrition live on every read: too slow, and it silently rewrites
history. Recomputing snapshots in a trigger: business logic in the database,
against DB-ADR-004's spirit and untestable in the Java test suite.

## DB-ADR-006 — Retirement and anonymisation instead of soft-delete columns

**Status:** Accepted

**Context.** Deleting a food that pantry items, plan entries and recommendation
history reference would destroy the project's most valuable data. Deleting a user
account must be possible for privacy reasons. A blanket `deleted_at` on every
table is the common reflex.

**Decision.** No `deleted_at` column anywhere. Instead:

- **Catalog rows are retired:** `foods.is_active`/`retired_at`,
  `ingredients.is_active`/`retired_at`, `recipes.status`
  (`DRAFT`→`PUBLISHED`→`ARCHIVED`), `ingredient_substitutions.is_active`. Paired
  `CHECK` constraints keep flag and timestamp consistent.
- **Catalog references use `ON DELETE RESTRICT`,** so a delete that would orphan
  history fails loudly.
- **Accounts follow deactivate → anonymise:** `deactivated_at` then
  `anonymized_at`, with `ck_users_anonymized_requires_deactivated` enforcing the
  order. Anonymisation overwrites `email` and `display_name`, invalidates
  `password_hash`, and deletes sessions, tokens, profile and body measurements,
  while the `users` row and the aggregate history survive.
- **Owned child data cascades** on a real user delete (`CASCADE` on every
  `user_id`), so full erasure remains a single statement.
- **Short-lived security rows are genuinely deleted** by a scheduled purge:
  expired `user_auth_sessions` and consumed `user_security_tokens`.

**Rationale.**

- A uniform soft delete forces every query in the system to carry
  `AND deleted_at IS NULL`. Forgetting it once leaks deleted data to a user, and
  it is forgotten eventually. Worse, unique constraints stop working as intended:
  a "deleted" row still occupies its unique email.
- Retirement is not soft deletion. It is a real domain state with different
  meaning per entity — a retired food should not appear in search but must stay
  attached to last month's meals; an archived recipe keeps its URL working.
- Anonymisation resolves the tension between the privacy obligation and the
  academic value of aggregate history. Deleting a user destroys their meal plans
  and recommendation outcomes, which are part of the evaluation dataset;
  anonymising removes the personal data and keeps the aggregates referentially
  valid.
- Keeping expired token hashes has no purpose and only enlarges the blast radius
  of a database compromise, so those rows go.

**Consequences.** Search and list queries filter on `is_active` / `status`, and
every index that serves them leads with that column, so the filter is free.
Anonymisation is a documented Java procedure with an integration test, not a
single `UPDATE`. Deleting a referenced food requires retiring it instead —
occasionally inconvenient for an administrator, and the correct default. A hard
`DELETE FROM users` still works for a full erasure request.

**Rejected alternatives.** `deleted_at` everywhere: query-predicate fragility and
broken uniqueness. `ON DELETE CASCADE` from the catalog: silent destruction of
history. Hard-deleting accounts only: loses aggregate history and forecloses
account recovery. An archive schema with copies: doubles the schema for no
question anyone will ask.

## DB-ADR-007 — Persist AI provenance, not AI intermediate state

**Status:** Accepted

**Context.** P1 ADR-003 and ADR-004 make Python stateless with no database
access; Java persists what it validates. That leaves the question of *how much* AI
output to keep. A single meal-plan generation may score thousands of candidates
and iterate an optimiser many times. Keeping everything gives perfect
reproducibility; keeping nothing makes the AI a black box and the report
unevidenced.

**Decision.** Persist four things, all written by Java:

1. **`recommendation_requests`** — that a request happened, its kind, target,
   status, timing, `correlation_id`, `algorithm_version`, `model_identifier`, and
   a `constraints_hash CHAR(64)` (SHA-256 of the normalised input snapshot).
2. **`recommendation_results`** — the shortlist actually returned to the user
   (typically 5–20 rows) with rank, subject, `total_score`, `explanation`, and the
   user's decision with `decided_at`.
3. **`recommendation_result_scores`** — the component breakdown, each row keyed to
   an `ai_score_components` row that declares the component's scale and direction.
4. **Provenance links** — `meal_plans.source_request_id` and
   `meal_plan_entries.source_result_id`, both `ON DELETE SET NULL`.

Do **not** persist: the full candidate set, per-iteration solver state, feature
vectors, embeddings, intermediate scores, or the raw AI response body.

**Rationale.**

- The questions that matter are answerable from the above: *what did the AI
  suggest, under which version, why (component scores), and did the user accept
  it?* Acceptance rate by `algorithm_version` — the headline AI-course result —
  needs only requests plus results, and
  `ix_recommendation_requests_algorithm_version` serves it.
- `constraints_hash` buys reproducibility without a copy of the user's profile,
  pantry and preferences on every request. That copy would be both a storage
  problem and a privacy problem — it would duplicate personal data into an
  append-only table that anonymisation could not reach.
- Storing every candidate would make this the largest table in the database by
  orders of magnitude and answer nothing. Offline algorithm evaluation belongs in
  a controlled export, which P1 ADR-004 already anticipated.
- `ai_score_components` declaring `scale_min`, `scale_max` and
  `higher_is_better` is what makes a stored `0.8` interpretable a year later.
  Without it, a score is an uninterpretable float — and a `DISLIKE_PENALTY` where
  lower is better would be read backwards.
- `SET NULL` on the provenance links means AI history can be pruned without
  touching an accepted meal plan. The plan is user data; the provenance is
  metadata about how it was produced.

**Consequences.** Java validates before persisting: recipe ids must exist, scores
must fall within their component's declared scale, and rank positions must be
distinct. An unvalidated AI response reaches no table. Python's contract must
report `algorithm_version` on every response. Deep post-hoc questions ("what was
ranked 400th?") cannot be answered from the database, which is the accepted
trade. The Python service remains free to keep whatever transient state it likes
in memory — it is not authoritative and does not survive the request.

**Rejected alternatives.** Persist every candidate: unbounded growth, no
consumer. Persist nothing: no evaluation, no explanation history, no way to
compare algorithm versions. Let Python write its own tables: forbidden by ADR-004,
and it would make AI failures transactional. A separate AI database: premature,
and already rejected in P1.

## DB-ADR-008 — Meal structure is data, not schema

**Status:** Accepted

**Context.** Meal planners commonly hardcode three meals a day —
`breakfast_recipe_id`, `lunch_recipe_id`, `dinner_recipe_id` on a day row. The
requirement is 3–7 day windows with configurable meal structures, and snacks,
brunch, or two-item dinners must not require a migration.

**Decision.** Nothing about meal structure is expressed in columns:

- Meal slots are rows in `meal_slot_types`, with `display_order`,
  `typical_time` and `is_main_meal`.
- `meal_plan_entries` is one row per planned item, unique on
  `(meal_plan_id, plan_date, meal_slot_type_id, position_in_slot)`.
- A day exists because entries reference its `plan_date`. There is no
  `plan_days` table; an unplanned day simply has no rows.
- `position_in_slot` allows several items in one slot.
- `meals_per_day_target` on the plan header is a nullable generation *hint*, not
  a constraint on rows.
- `ck_meal_plans_window` permits 1–31 days.

**Rationale.** Fixed meal columns fail immediately: a user who skips breakfast
stores a NULL that is indistinguishable from an unplanned breakfast; a user who
wants a mid-afternoon snack needs a migration; a dinner of a main plus a side
cannot be expressed at all. Rows also make the plan screen a simple ordered read,
and `recipe_meal_slot_types` gives generation a direct filter for "recipes
suitable for breakfast" — impossible against a column name.

The 31-day ceiling is a sanity bound against a data-entry error creating a
ten-year plan, not a product limit; it comfortably contains the 3–7 day target.

**Consequences.** Rendering a week requires grouping entries by date and slot in
Java rather than reading one row per day — a small amount of code, written once.
An empty slot is represented by absence, so the UI must decide what to display for
a gap. Adding a meal slot is a seed row in `R001`.

**Rejected alternatives.** Fixed meal columns: cannot express the required
flexibility. A `plan_days` table enumerating each date: rows that carry no
information beyond a date already derivable from the plan window. A JSON plan
document: fails DB-ADR-002 on partial update and aggregation. An unbounded plan
window: no sanity check against absurd input.

## DB-ADR-009 — Substitutions are typed, directed edges

**Status:** Accepted

**Context.** "You can use X instead of Y" is not a symmetric, context-free,
one-to-one relation, but the naive models all assume it is. An equivalence-group
model ("these are interchangeable") is the most tempting and the most dangerous:
it would let the system tell an allergic user that almond milk substitutes for
cow's milk in a recipe where the reverse was what was safe.

**Decision.** Two mechanisms with different strengths of claim.

`ingredient_groups` + `ingredient_group_members` express loose culinary families
and are used only to **widen candidate search**. Membership asserts nothing about
interchangeability.

`ingredient_substitutions` is the assertion, as a directed edge from
`original_ingredient_id` to `substitute_ingredient_id`, unique on
`(original, substitute, substitution_context)`, carrying:
`substitution_context`, `ratio_numerator`/`ratio_denominator`, `confidence`,
`preserves_allergen_profile`, `sensory_impact`, `guidance`, `source_note`,
`is_active`.

**Rationale.**

- **Direction.** Greek yoghurt for sour cream is fine; sour cream for Greek
  yoghurt in a marinade is not. A symmetric table cannot express that, and
  automatically reversing an edge would invent a claim nobody made.
- **Context.** Butter→oil works when frying and fails in shortcrust pastry. One
  row per `(pair, context)` means the same pair can be safe in one context and
  simply absent in another — absence being the correct answer, not a fallback to
  "general".
- **Exact ratios.** `ratio_numerator`/`ratio_denominator` as separate decimals
  keeps 3/4 exact rather than 0.75-rounded, and the arithmetic composes without
  accumulating error.
- **Allergen safety is not delegated to this table.**
  `preserves_allergen_profile` is a hint; the binding check is Java re-querying
  `ingredient_allergens` for the substitute against `user_allergens`. A
  substitution edge is a culinary claim, never a medical clearance.
- **`sensory_impact` and `guidance`** let the client warn rather than silently
  change a dish, and `guidance` holds the caveat no enumeration captures.
- **`is_active`** withdraws a bad edge while keeping the record that it was
  suggested — relevant if it ever reached a user.

**Consequences.** The substitution catalog must be curated pair by pair with a
context, which is slower than declaring groups and is the point: an unsafe
substitution cannot be created by accident. Java queries
`ix_ingredient_substitutions_original (original_ingredient_id,
substitution_context, is_active)` and must handle "no substitution known" as a
normal outcome. Python may rank candidate substitutions but must not invent edges.

**Rejected alternatives.** Symmetric equivalence groups: unsafe, as above. A
single context-free `substitutes_for` table: hides the context where the swap
fails. A numeric similarity score alone: unexplainable to a user and unable to
carry a ratio or a warning. Letting the AI service generate substitutions at
runtime with no stored catalog: no review path, no provenance, no way to withdraw
a bad suggestion.

## DB-ADR-010 — Relational full-text search, not an external search engine

**Status:** Accepted

**Context.** Recipe, food and ingredient search is a core feature. Elasticsearch,
OpenSearch, Meilisearch and pgvector-style vector search are the usual answers,
and an AI project invites the argument that semantic search needs embeddings.

**Decision.** P2 introduces no external search infrastructure. Search is served
by MySQL: three InnoDB `FULLTEXT` indexes (`ftx_foods_name_brand`,
`ftx_ingredients_name`, `ftx_recipes_title_summary`), composite B-tree indexes for
filtering and sorting, and `ingredient_aliases` for synonyms.

**Rationale.**

- The catalog will hold thousands of rows, not millions. InnoDB full-text with
  `MATCH ... AGAINST` handles relevance ranking and boolean mode comfortably at
  that size.
- A search engine is a second datastore: it needs indexing pipelines,
  reindex-on-change, staleness handling, a deployment, and a failure mode where
  search silently returns stale results. For a four-person team that cost is not
  repaid by better recipe search.
- It would also weaken ADR-004's single-owner property. Every replicated index is
  a second copy of data with its own consistency window.
- Vector search would need an embedding model, an embedding pipeline, storage,
  and a similarity index — and the AI value in this project is in recommendation
  (constraint satisfaction, scoring, optimisation over pantry, nutrition and
  preferences), not in fuzzy text matching. Spending the AI budget on search would
  be spending it in the wrong place.
- Most real search here is *structured*, not textual: diet tags, cooking time,
  available ingredients, meal slot. Composite indexes serve those better than any
  text engine.

**Accepted limitations.** No fuzzy/typo tolerance, weak stemming for Vietnamese,
no semantic similarity, a default minimum token length, and stopword handling that
needs configuration. `ingredient_aliases` mitigates the synonym case, which is the
most common real complaint.

**Consequences.** Search stays a Java module reading MySQL, exactly as P1 section
9.1 describes, with no new deployable. The migration path is additive: if measured
search quality or latency becomes a problem, a future ADR can introduce a search
service fed from MySQL, with MySQL still authoritative — no data migration
required, only an indexing pipeline. `search_queries` collects the evidence for
that decision by recording zero-result queries.

**Rejected alternatives.** Elasticsearch now: operational cost and a second
datastore before any measurement. A vector database now: solves a problem this
product does not have, at the expense of the AI work that matters. `LIKE
'%term%'`: cannot use an index at all and would be slower than full-text.

## DB-ADR-011 — Two roles, not a permission matrix

**Status:** Accepted

**Context.** The schema needs an authorization model. The textbook answer is
users → roles → permissions → resources, and it is easy to build early. The
product has exactly one privileged activity: curating the food and recipe catalog.

**Decision.** `roles` and `user_roles` only, seeded with `ROLE_USER` and
`ROLE_ADMIN`. No `permissions` table, no `role_permissions`, no resource-scoped
grants, no role hierarchy. `user_roles` records `granted_at` and `granted_by`
(`ON DELETE SET NULL`).

**Rationale.** A permission matrix is only useful when permissions vary
independently of roles. With two roles and one privileged activity, every
permission row would be derivable from the role, so the extra tables would encode
no information while adding two joins to every authorization check. Ownership
checks — "is this your pantry item?" — are `WHERE user_id = ?`, which no RBAC
system improves.

`ROLE_ADMIN` is a real need: someone must correct a wrong nutrition value or
withdraw a bad substitution edge, and that must not be available to every user.

**Consequences.** Spring Security uses `hasRole('ADMIN')` and method-level checks
against ownership. If a third role appears (a nutritionist who can edit foods but
not manage accounts), a `permissions` table can be introduced additively — the
`user_roles` data survives, because roles remain the grant unit. Java must not
hardcode `role_id` values; it keys on `roles.code`.

**Rejected alternatives.** Full RBAC with permissions: speculative structure for
requirements that do not exist. A boolean `is_admin` on `users`: cheaper still,
but it cannot record who granted the privilege or when, and adding a third role
would mean a migration and a data conversion. Per-resource ACLs: nothing in this
product shares resources between users.

## DB-ADR-012 — Unit conversion is ingredient-specific and may be unknown

**Status:** Accepted

**Context.** Recipes measure in cups, tablespoons and pieces; nutrition data is
per 100 g or 100 ml; pantry stock is in whatever the packaging said. Something
must reconcile them. The tempting shortcut is a global conversion table with a
row like "1 tbsp = 15 g".

**Decision.** Conversion is layered by what is actually knowable:

1. **Exact, universal:** mass↔mass and volume↔volume, via
   `measurement_units.base_unit_id` + `factor_to_base_unit` (kg→g, tbsp→ml). A
   base unit has neither column set; a derived unit has both, enforced by
   `ck_measurement_units_conversion`.
2. **Ingredient-specific:** volume↔mass and count↔mass, via
   `ingredient_unit_conversions` — an exact pair
   (`from_quantity from_unit` = `to_quantity to_unit`) with `confidence` of
   `MEASURED` / `REFERENCE` / `ESTIMATED`. Plus `ingredients.piece_gram_weight`
   for the common "one medium onion" case and `foods.density_g_per_ml` where a
   density is genuinely known.
3. **Serving-level:** `food_servings` maps a household serving to `gram_weight`
   or `milliliters`, which is how a "1 cup, chopped" nutrition lookup resolves.
4. **Unknown:** when no path exists, the answer is unknown and Java must say so.

The schema stores **no** generic volume→mass factor.

**Rationale.** A cup of flour is about 120 g and a cup of honey about 340 g. Any
single tbsp→gram factor is wrong for most ingredients, and being wrong here
corrupts nutrition totals — the number the product exists to report. Storing an
average would make the error invisible, which is worse than refusing.

`confidence` is what keeps the data honest: a value measured by the team, taken
from a reference table, or guessed are different kinds of fact, and a nutrition
total assembled from guesses should be labelled.

Storing ratios as an exact `from_quantity`/`to_quantity` pair rather than a single
factor avoids repeated rounding when conversions compose.

**Consequences.** Java's conversion service returns an explicit "cannot convert"
outcome, and every caller — recipe scaling, pantry deduction, nutrition
computation — must handle it. The UI should steer users toward units the
ingredient has conversions for. `recipe_nutrition_snapshots.completeness_ratio`
is where a failed conversion becomes visible instead of silently producing a low
total. Populating `ingredient_unit_conversions` is ongoing curation work, and the
catalog is useful before it is complete.

**Rejected alternatives.** A global unit conversion table: silently wrong for most
ingredients. Assuming water density (1 g/ml) for everything: wrong for oil,
flour, honey, and most solids. Requiring mass units everywhere: real recipes and
real packaging do not work that way. Refusing to store any count units: "2 eggs"
is the natural expression and `piece_gram_weight` handles it.

## DB-ADR-013 — Ingredients and foods are separate entities

**Status:** Accepted

**Context.** "Chicken breast" is one thing to a cook and several things to a
nutrition database — raw, grilled, breaded, canned — each with different nutrition
per 100 g. A single `foods` table serving both roles is the obvious first model.

**Decision.** Two entities. `ingredients` is the **culinary identity** used by
recipes, pantry items, substitutions, dislikes and allergen mapping. `foods` is
the **nutritional record**, with `nutrition_basis`, `food_nutrients` and
`food_servings`. `ingredient_foods` maps between them with `preparation_state`,
`yield_factor` and `is_primary`; `ingredients.default_food_id` shortcuts to the
primary mapping.

**Rationale.**

- The relationship is many-to-many in both directions. One ingredient maps to
  raw/cooked/canned nutrition records; one food ("olive oil, extra virgin") serves
  as the nutrition record for one ingredient but may be shared across brand
  variants.
- Everything the *user* touches is an ingredient. A pantry item is "chicken
  breast", not "chicken breast, raw, USDA 05062". Forcing a nutrition-record
  choice into pantry entry would make the feature unusable.
- Substitution operates on culinary identity. "Use yoghurt instead of sour cream"
  is a claim about ingredients; asserting it between nutrition records would
  require repeating it for every preparation variant.
- `yield_factor` records cooking mass change, which only exists as a property of
  the ingredient→food(prepared) edge — it has no home in a single-table model.
- One merged table would need nullable nutrition columns for every culinary-only
  row and duplicate culinary metadata across preparation variants, guaranteeing
  divergence.

**Consequences.** Nutrition lookup is a two-hop join (ingredient → food →
nutrients), which `ix_ingredient_foods_food` and the `food_nutrients` primary key
serve. Catalog curation maintains both tables and their mapping. `recipe_ingredients`
and `pantry_items` reference an ingredient and *may* pin a `food_id` when a recipe
specifically means the canned version. An ingredient with no food mapping is valid
and simply has no nutrition — surfaced through `completeness_ratio`.

**Rejected alternatives.** One `foods` table for both: forces users to pick
nutrition records, breaks substitution, has no home for yield. Ingredient as a
free-text string on `recipe_ingredients`: no allergen mapping, no pantry matching,
no substitution, no nutrition. A generic self-referencing "food item" hierarchy:
one table pretending to be two, with the distinction moved into a `kind` column
and every constraint made conditional.

## DB-ADR-014 — Unknown expiry is represented as unknown

**Status:** Accepted

**Context.** Prioritising soon-to-expire ingredients is a headline feature, so
expiry date looks like a required field. In a real kitchen most items have no
usable date: loose vegetables, bulk rice, an opened jar, anything decanted. The
convenient options are a `NOT NULL` column with an estimated default, or a
sentinel like `9999-12-31`.

**Decision.** `expiry_date` is nullable, and its absence is stated explicitly
across three columns tied together by `ck_pantry_items_expiry_consistency`:
`expiry_date IS NULL` **if and only if** `expiry_kind = 'UNKNOWN'` **and**
`expiry_confidence = 'UNKNOWN'`. When a date is present, `expiry_kind` is
`USE_BY` or `BEST_BEFORE` and `expiry_confidence` is `LABELLED` or `ESTIMATED`.
No sentinel dates.

**Rationale.**

- A defaulted estimate is a fabricated fact. It would drive notifications and
  recommendations that claim knowledge the system does not have — and in the
  wrong direction it implies food is safe when nobody checked.
- `USE_BY` versus `BEST_BEFORE` is a safety distinction: a recommender may
  reasonably push a best-before item slightly past its date and must never push
  past a use-by date. Collapsing them into "expiry" removes the ability to behave
  correctly.
- `LABELLED` versus `ESTIMATED` records how the date was obtained, so the UI can
  present an estimate as an estimate. `ingredients.typical_shelf_life_days` lets
  Java *offer* an estimate at entry time, recorded as `ESTIMATED` — never
  promoted to `LABELLED`.
- The three-way `CHECK` prevents the state that would otherwise appear from a
  partial update: a NULL date with `expiry_kind = 'USE_BY'`, which reads as "there
  is a safety deadline and we lost it".
- Sentinel dates were rejected because they participate in comparisons. `MIN` and
  `ORDER BY` treat `9999-12-31` as a real date, and every query would need to
  exclude it — the same fragility as a soft-delete predicate.

**Consequences.** `ix_pantry_items_user_expiry (user_id, status, expiry_date)`
serves the expiring-soon query, with a documented trap: MySQL sorts NULLs first
ascending, so an unknown expiry masquerades as the most urgent item. Java must add
`expiry_date IS NOT NULL`, and this is noted in the schema comments, in the data
model and in the dictionary. The UI needs a third state — "no expiry date" — in
the pantry list, and the recommender treats unknown-expiry items as unprioritised
rather than urgent. Users can add a date later; `ck_pantry_items_expiry_after_acquired`
keeps it consistent with `acquired_on`.

**Rejected alternatives.** `NOT NULL` with a default from typical shelf life:
fabricates safety information. A sentinel far-future date: pollutes every
comparison. A single boolean `expiry_known`: cannot distinguish a use-by from a
best-before, nor a label from a guess. A separate `pantry_item_expiry` table:
one-to-one with the item, no benefit.

## DB-ADR-015 — Targeted history tables, not a generic audit log

**Status:** Accepted

**Context.** Requirement L asks for high-value history. The generic answer is an
`audit_log` table — entity name, entity id, action, actor, timestamp, and a
serialised before/after payload — populated for every write.

**Decision.** No generic audit table. History exists where a specific question
needs it: `user_body_measurements`, dated `user_nutrition_targets`,
`pantry_item_events`, `meal_plan_entries.consumption_status`,
`recommendation_requests`/`_results`, `recipe_nutrition_snapshots`,
`user_account_events` (14 enumerated security-relevant event types), and
`search_queries`.

**Rationale.**

- A generic audit table is unqueryable in practice. "How has this user's weight
  changed?" becomes parsing JSON payloads out of a table containing every write in
  the system, with no type safety and no index that helps.
- It becomes the largest table in the database, holding mostly rows nobody reads,
  and it duplicates personal data into a place anonymisation cannot reach —
  a privacy problem created by an audit feature.
- Each targeted table is typed, indexed for its question, and constrained.
  `pantry_item_events.quantity_delta`/`quantity_after` make waste measurement a
  `SUM`, not a parse.
- `user_account_events` is where a security trail genuinely belongs, and bounding
  it to 14 event types keeps it a security log rather than a write log. Its
  retention is shorter than the account's, because it exists for incident
  investigation.
- `ip_address VARBINARY(16)` (via `INET6_ATON`) holds IPv4 and IPv6 in one
  column and sorts correctly, unlike a string form.

**Consequences.** Adding history for a new concern is a deliberate design step
with a stated question, not a free side effect. Changes to tables with no history
table are not recoverable from the database — accepted, because those are current
state that the user can correct. Every history table is append-only with a single
timestamp and no `updated_at`, so "correcting" history means a new row.

**Rejected alternatives.** A generic `audit_log`: unqueryable, oversized, and a
privacy liability. Hibernate Envers: automatic versioning of every entity, roughly
doubling the table count with `_AUD` tables nobody queries. Database triggers
writing audit rows: business logic in the database, invisible to the Java tests.
No history at all: the report has no data and the pantry cannot explain a quantity
change.

## DB-ADR-016 — MySQL 8 on InnoDB with utf8mb4

**Status:** Accepted (inherited from P1 ADR-004)

**Context.** P1 fixed MySQL as the durable store. P2 must pin the version,
engine, character set and collation, because several design choices depend on
features that MySQL 5.7 lacks.

**Decision.** MySQL **8.0.19 or later**, InnoDB, `utf8mb4` with
`utf8mb4_0900_ai_ci` on every table.

**What requires MySQL 8 specifically:**

| Feature | Used for |
| --- | --- |
| Enforced `CHECK` constraints (8.0.16+) | All 125 checks. MySQL 5.7 parses and ignores them, which is worse than not having them. |
| Functional indexes (8.0.13+) | `ux_food_servings_food_default`, `ux_ingredient_foods_primary`, `ux_recipe_nutrition_snapshots_current` — "at most one default" without a trigger. |
| Row alias in `INSERT ... ON DUPLICATE KEY UPDATE ... AS new` (8.0.19+) | The seed file, avoiding the deprecated `VALUES()` function. |
| `utf8mb4_0900_ai_ci` | Accent-insensitive Vietnamese search. |
| Common table expressions | Recursive `food_categories` traversal in later queries. |
| Window functions | Ranking and running totals in reporting queries. |

`utf8mb4` is not optional: MySQL's legacy `utf8` is `utf8mb3` and cannot store a
four-byte character, so an emoji in a recipe title would be silently mangled.
`utf8mb4_0900_ai_ci` is accent- and case-insensitive, so "che" matches "chè" and
"Pho" matches "phở" — required behaviour for a Vietnamese food catalog.

**Consequences.** MySQL 5.7 is not supported, which is deliberate — deploying
there would silently discard every `CHECK` constraint. Local development needs
MySQL 8.x; the version was verified against 8.4.11. JDBC uses
`mysql-connector-j` 8.x with `connectionTimeZone=UTC`. MariaDB is not a supported
target: its `CHECK` and functional-index behaviour and its collation names differ.

**Rejected alternatives.** PostgreSQL (better constraint and JSON support, real
partial indexes) is excluded by the locked stack in P1 ADR-004. MySQL 5.7:
ignored `CHECK` constraints. MyISAM: no transactions, no foreign keys, not a
candidate.

## DB-ADR-017 — Java is the only database client

**Status:** Accepted (implements P1 ADR-004)

**Context.** P1 ADR-004 states that only Spring Boot accesses MySQL, and that
Flutter and Python hold no credentials. This record states what that means for the
schema, because a design can technically violate it while every diagram still
claims otherwise.

**Decision.** The schema is designed for exactly one writer. Specifically:

- No database `VIEW`, stored procedure, function, trigger or event is created
  for any consumer. The only database-side computation is three generated columns
  and `ON UPDATE CURRENT_TIMESTAMP` defaults.
- No table exists as an integration surface — no outbox for Python, no
  Python-writable scratch table, no shared queue table.
- No `CREATE USER` or `GRANT` appears in any migration, so the schema files
  encode no second identity that could become a second client.
- Every AI-related table (`recommendation_requests`, `recommendation_results`,
  `recommendation_result_scores`) is written by Java after validation. Python's
  contribution arrives as an HTTP response body.
- Business invariants live in `CHECK` constraints and foreign keys — declarative,
  writer-agnostic — plus Java service logic. None live in database procedures,
  which would create a second place where domain rules are enforced.

**Rationale.** A single writer is what makes the invariants in this design
trustworthy. `pantry_items.quantity_remaining` staying consistent with
`pantry_item_events`, `is_current` marking exactly one nutrition snapshot, and
`meal_plans.status` matching its timestamps are all guarantees of a transaction
boundary that only one writer can hold. Any second writer — a script, a reporting
tool, a Python job — would need to reimplement those rules, and would eventually
diverge.

Giving Python database access would additionally make AI failures transactional:
an unhealthy AI service could hold locks or write partial state, breaking the
degraded path that P1 section 7.5 depends on.

**Consequences.** Reporting and offline evaluation use Java-provided exports or a
read path Java exposes, not a direct connection. Database credentials exist only
in the Spring Boot environment. Manual administrative fixes are migrations or
Java-side operations, reviewed like any other change; ad-hoc SQL against a
populated database is not a supported workflow. The isolated, throwaway MySQL
instance used to validate P2 is a development tool, not a component.

**Rejected alternatives.** A read-only database user for Python: still a second
connection and a credential to manage, and read access to the full schema exceeds
what the AI contract needs. An outbox table Python polls: makes Python a database
client and adds a coupling ADR-005 (REST) already covers. Views for reporting:
another consumer coupled to schema details.

## DB-ADR-018 — Third normal form, with three documented exceptions

**Status:** Accepted

**Context.** Normalization needs a stated target so that reviewers can judge
whether a given denormalisation is deliberate or accidental.

**Decision.** Third normal form for operational data. Exactly three departures,
each recorded in [DB-ADR-005](#db-adr-005--derived-values-are-computed-not-stored-except-as-dated-snapshots):
`STORED` generated columns, recipe nutrition snapshots, and
`pantry_items.quantity_remaining`. No other duplicated data exists.

**Rationale.** 3NF removes the update anomalies that matter here. Nutrient units
live on `nutrients`, not on every `food_nutrients` row, so protein cannot be
grams for one food and milligrams for another. A recipe's ingredient names live on
`ingredients`, so renaming an ingredient does not require touching thousands of
recipe lines. Allergen data lives on `ingredient_allergens`, so it cannot say
"contains peanuts" in one recipe and not another.

Higher normal forms (BCNF, 4NF) were considered and found to make no difference:
no table has overlapping candidate keys or independent multivalued dependencies
that would violate them.

The three exceptions are each justified by a specific cost that normalization
imposes and a specific mechanism that keeps the redundancy honest — MySQL
maintaining a generated column, a snapshot's `computed_at`/`ingredient_revision`
recording what it was derived from, and a `CHECK` bounding
`quantity_remaining`.

**Consequences.** Read queries join more. This is the correct trade at this data
volume with these indexes, and a measured slow query is grounds for a new
migration and a new record here — not for quietly adding a duplicated column.
Any future denormalisation must state the query it serves, the mechanism that
keeps it consistent, and who maintains it.

**Rejected alternatives.** A denormalised read model (a wide `recipe_search`
table): premature, and a second copy to keep in step. Star-schema-style
dimensional modelling: this is an operational database, not a warehouse. Strict
3NF with no exceptions: would mean recomputing recipe nutrition on every read and
rewriting history when a food is corrected.
